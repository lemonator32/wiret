In computer programming education, a **visual programming language**, **block coding system** or **diagrammatic programming language**, is a programming language that lets users create programs by manipulating program elements *graphically* rather than by specifying them *textually*. A VPL allows programming with visual expressions, spatial arrangements of text and graphic symbols, used either as elements of syntax or secondary notation. For example, many VPLs are based on the idea of "boxes and arrows", where boxes or other screen objects are treated as entities, connected by arrows, lines or arcs which represent relations. VPLs are generally the basis of low-code development platforms. Scratch is an example of a VPL.

## Definition

VPLs may be further classified, according to the type and extent of visual expression used, into icon-based languages, form-based languages, and diagram languages. Visual programming environments provide graphical or iconic elements which can be manipulated by users in an interactive way according to some specific spatial grammar for program construction.

The general goal of VPLs is to make programming more accessible to novices and to support programmers at three different levels:

**Syntax**

VPLs use icons/blocks, forms and diagrams trying to reduce or even eliminate the potential of syntactic errors helping with the arrangement of programming primitives to create well-formed programs.

**Semantics**

VPLs may provide some mechanisms to disclose the meaning of programming primitives. This could include help functions providing documentation functions built-in to programming languages.

**Pragmatics**

VPLs support the study of what programs mean in particular situations. This level of support allows users to put artifacts created with a VPL into a certain state in order to explore how the program will react to that state. Examples: In AgentSheets or AgentCubes users can set games or simulations into a particular state in order to see how program would react. With the Thymio programming language users can bring a robot into a certain state in order to see how it will react, i.e., which sensors will be activated.

As of 2005, current developments try to integrate the visual programming approach with dataflow programming languages to either have immediate access to the program state, resulting in online debugging, or automatic program generation and documentation. Dataflow languages also allow automatic parallelization, which is likely to become one of the greatest programming challenges of the future.

The Visual Basic, Visual C#, Visual J# etc. languages of the Microsoft Visual Studio integrated development environment (IDE) are *not* visual programming languages: the representation of algorithms etc. is textual even though the IDE embellishes the editing and debugging activities with a rich user interface. A similar consideration applies to most other rapid application development environments which typically support a form designer and sometimes also have graphical tools to illustrate (but not define) control flow and data dependencies.

Parsers for visual programming languages can be implemented using graph grammars.

## Types of visual languages

The following list is not mutually exclusive, as some visual programming environments may incorporate elements from multiple paradigms. The choice of visual programming paradigm often depends on the specific requirements of the application or the preferences of the users or the developers.

- **Block-based programming**: Popularized by platforms like Scratch and Blockly, used in educational settings and for introductory programming.
- **Flowcharts**: Widely used in software engineering and systems design for representing algorithms and processes.
- **Drag and drop interfaces**: Commonly used in GUI design tools and development environments for creating user interfaces.
- **Node graphs**: Frequently used in visual programming languages, game development, and dataflow systems.
- **Dataflow programming**: Popular in parallel computing, signal processing, and visual programming environments.
- **Iconic programming**: Used in various contexts for simplifying programming tasks, often associated with mobile app development.
- **State machines**: Widely employed in game development, control systems, and modeling reactive systems.
- **Sheet-based programming**: Found in spreadsheet applications and certain educational programming environments.
- **Timeline-based programming**: Common in multimedia and animation software for sequencing events over time.
- **Spatial programming**: Applied in certain interactive and 3D modeling environments.
- **Form-based programming**: Used in applications where user input and graphical interfaces play a significant role, such as data entry applications.

## General-purpose visual languages

Most of the VPLs are designed for education or domain-specific usage where the target users are novice programmers. But there are some research projects try to provide a general-purpose visual programming language that can be used by mainstream programmers in any software project instead of using textual programming languages (like C, C++, Java, etc.).

For example, research projects such as PWCT and Envision was designed to achieve this goal.

## Visual Programming Languages: Computational Models and Design

The foundational material surveys visual programming languages (VPLs), including educational block coding, scientific simulation, game development, multimedia, and business automation. The following sections examine what makes a visual notation a programming language, how computational models differ, why some approaches scale better than others, and what general-purpose visual programming requires.

The discussion extends these distinctions with computer science concepts, historical context, design analysis, and research questions, while distinguishing added analysis from the source material.

### 1. What is a visual programming language?

The central idea is simple: a visual programming language represents programs through graphical structures that users manipulate directly, rather than relying exclusively on textual source code. Three broad forms are commonly identified:

- Icon-based languages: icons represent operations, objects, or actions.
- Form-based languages: users configure structured fields, properties, and relationships.
- Diagrammatic languages: nodes, blocks, lines, arrows, and spatial arrangements represent computational structures.

These categories overlap. A single environment might use blocks to express control flow, forms to configure parameters, and a node graph to process data.

These are not four mutually exclusive language classes. Block-based programming describes a notation and editing approach; dataflow describes a computational model; model-based programming describes a broader way of specifying systems. A node editor may combine all three.

#### The crucial distinction: visual editor versus visual language

A graphical interface does not automatically make a programming language visual.

Consider three applications:

1. A text editor with syntax highlighting and autocomplete.
2. A graphical interface that lets you design a form but generates a fixed application template.
3. A node editor where connecting nodes defines the actual computation.

Only the third is unambiguously a visual programming environment in the strong sense. The second may be a visual authoring or model-driven development tool, depending on how much behavior the user can specify. The first remains a textual programming environment.

This clarifies the Wikipedia article's distinction between languages such as Scratch and environments such as Visual Studio: the important question is how the program's meaning is expressed, not how sophisticated its interface looks.

### 2. The three levels of visual programming: syntax, semantics, and pragmatics

One of the most useful ideas in your Wikipedia article is its distinction between syntax, semantics, and pragmatics. These are not just abstract terminology; they provide a framework for evaluating whether a visual language is well designed.

Syntax — Can I construct a valid program?

Visual languages can enforce structural rules through block shapes, connection types, required inputs, and restricted placement. A Boolean value, for example, might fit into a condition socket but not into a connection that expects an executable statement.

Design objective: prevent invalid constructions before execution.

Semantics — What does this program mean?

The language must define what each block or node does and how components interact. A node labeled “Add” needs rules for input types, output values, evaluation order, and errors.

Design objective: make behavior precise, predictable, and understandable.

Pragmatics — How does it behave in a real situation?

Users need to understand how the program responds to actual inputs, events, world states, and environmental conditions. A robot's behavior may depend on sensor readings; a game character may respond differently depending on its health or location.

Design objective: support experimentation, feedback, testing, and debugging.

The distinction reveals an important limitation: a language can make programs easy to construct without making them easy to understand or debug.

Interlocking blocks may prevent syntax errors, but they cannot prevent a programmer from implementing the wrong algorithm. A type-correct node graph may still produce incorrect results. A simulation may behave correctly in one tested scenario while failing in another.

This suggests a useful design principle: a good VPL should not merely constrain construction. It should also communicate meaning and make program behavior observable.

The article's discussion of immediate feedback and online debugging is particularly relevant here. Research into visual programming has long examined program comprehension, construction, and debugging as separate problems; the evidence does not establish that every visual representation improves all three equally.&#x20;

### 3. A deeper taxonomy: visual notation is not the same as computational model

The Wikipedia article lists blocks, flowcharts, node graphs, dataflow, state machines, spreadsheets, timelines, and spatial programming. This is a useful catalog, but the categories mix different dimensions.

For research purposes, it is better to distinguish at least four questions:

- Representation: What does the program look like?
- Computation: What rules determine its execution?
- Interaction: How does a programmer construct and modify it?
- Purpose: What kinds of problems is it intended to solve?

A visual language may use a graph as its representation but implement imperative control flow, dataflow, event-driven behavior, or a mixture of these.

This is a key point for comparing languages: two systems can look almost identical yet have fundamentally different semantics.

#### Why dataflow deserves special attention

Dataflow is one of the most influential foundations for visual programming. A graph can directly represent the relationships between values and computations, which is particularly useful when the problem itself consists of transformations.

Consider a simple calculation:

Input A

Value: 12

Multiply

A × B

Output

### 36

12 × 3

In an actual graph, the Multiply node would have two input connections, not one. The important feature is that the graph represents dependencies: the output depends on both input values and the multiplication operation.

This representation can make data transformations easier to inspect. It also raises questions that a language designer must answer:

- Does a node execute once, whenever an input changes, or whenever an execution signal arrives?
- Are connections values, messages, references, or streams?
- Are cycles allowed, and if so, how are they evaluated?
- Can independent operations execute in parallel?
- What happens when a node fails or an input is missing?

These are semantic questions, not merely visual-design questions. The classic literature on dataflow languages identifies a broad range of design alternatives and unresolved implementation issues.&#x20;

### 6. The major strengths of visual programming

Visual programming's benefits are not automatic properties of graphics. They arise when a representation and its interaction model suit the task.

#### A. Structural validity

A well-designed editor can make many invalid programs impossible to construct. Typed connection ports, compatible block shapes, and required fields can enforce parts of the language grammar during editing.

This is a stronger guarantee than merely displaying an error after the program is parsed. But it only addresses the constraints the language encodes.

#### B. Externalizing relationships

Graphs make dependencies visible. Instead of mentally reconstructing which operation supplies which value, users can often follow the connections directly.

This can be especially valuable for:

- Data transformations.
- Signal processing.
- Event-driven behavior.
- System architecture.
- Procedural modeling.
- State transitions.

The benefit depends on graph size, layout, and the quality of the visual notation.

#### C. Direct manipulation

Users can create and modify programs by connecting components, changing parameters, moving structures, and selecting operations from menus.

This lowers the need to memorize exact syntax, but it introduces its own interaction costs: navigating large canvases, managing connections, and manipulating small interface elements.

#### D. Domain-specific expression

A domain-specific visual language can expose concepts that users already understand. A scientist might manipulate signals and equations; an artist might manipulate geometry and effects; an automation engineer might manipulate events and devices.

This allows a language to hide implementation details without necessarily sacrificing expressiveness within its intended domain.

#### E. Immediate feedback and experimentation

When a program can be executed or simulated during construction, users can observe its behavior as they work. Some environments support live values, interactive simulation, or visual debugging.

This can turn programming into a cycle of construction, observation, and refinement rather than a strictly linear process.

#### F. Shared communication

Visual programs can act as documentation. A workflow, control system, or procedural network may be easier for a multidisciplinary team to discuss when the relationships between components are explicit.

However, this advantage diminishes if the diagram becomes too large, relies on undocumented conventions, or hides important behavior inside custom nodes.

### 7. The major weaknesses and trade-offs

The most important research question is not whether visual programming is good or bad. It is which costs the representation removes, and which costs it introduces.

| Challenge        | Why it matters                                                                  | Possible design response                                        |
| ---------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Graph complexity | Large programs require extensive navigation and create visual clutter.          | Hierarchical graphs, modules, grouping, semantic zoom           |
| Spatial overhead | Connections, nodes, and labels occupy screen space.                             | Compact layouts, folding, minimaps, multiple views              |
| Refactoring      | Moving or restructuring connected components can require many edits.            | First-class functions, abstraction, safe automated rewrites     |
| Version control  | Graphical files can produce noisy diffs and merge conflicts.                    | Stable identifiers, canonical serialization, semantic diffs     |
| Debugging        | A valid graph may still encode incorrect behavior.                              | Breakpoints, traces, value inspection, test generation          |
| Abstraction      | Repeated patterns may become large subgraphs.                                   | Reusable functions, components, libraries, parameterized graphs |
| Precision        | Textual code can be faster for dense symbolic expressions and repetitive edits. | Embedded expressions, text shortcuts, hybrid editing            |
| Accessibility    | Color, spatial placement, and drag-and-drop can exclude some users.             | Keyboard navigation, screen-reader semantics, non-color cues    |
| Portability      | A program may depend on a particular editor or runtime.                         | Open formats, documented semantics, code generation             |
| Performance      | A visual graph may not map efficiently to the target runtime.                   | Compilation, optimization, profiling, execution planning        |

A systematic review of visual programming approaches for end-user developers highlighted a particularly important gap: many tools were studied with novices, but relatively few received formal experimental evaluation, and expressiveness was rarely evaluated. The review also identified lifecycle support, learnability, and debugging as areas requiring more attention.&#x20;

#### A deeper problem: spatial organization can become accidental semantics

In some visual languages, spatial layout is merely a way to organize the program. In others, position or proximity carries actual meaning.

This distinction matters because programmers often use layout as informal documentation: related nodes are placed near one another, groups are arranged from left to right, and colors distinguish subsystems.

These cues can improve readability, but they can also become fragile. If moving a node changes execution semantics, the language must make that behavior explicit. If moving a node changes nothing semantically, the editor should preserve enough freedom to organize the graph without fear of altering the program.

This leads to a useful design principle:

Keep program meaning explicit, and make visual organization support that meaning rather than obscure it.

### 8. How should a visual programming language be designed?

If your goal is to research VPLs as a field rather than just catalog existing products, this is arguably the most important section.

A VPL is simultaneously a language, a visual notation, an editing environment, and often a runtime. A strong design must account for all four.

#### 8.1 Define the computational model first

Before choosing node shapes or colors, specify what programs mean.

For example:

- Is execution sequential, data-driven, event-driven, reactive, or concurrent?
- What are the language's values and types?
- What is the scope and lifetime of variables?
- How are functions and reusable components represented?
- How are errors, exceptions, and cancellation handled?
- Are programs deterministic?
- Can programs interact with external systems?

A graph editor is not a computational model. It is a way to express one.

#### 8.2 Make the grammar enforceable

The editor should know which constructions are valid.

A language might define distinct connection types:

Control

Execution connections

Specify which operation or branch runs next.

Data

Value connections

Specify how results flow between operations.

Events

Event connections

Specify which handlers respond to messages, signals, or occurrences.

These connection classes are an illustrative design, not a universal standard. Their purpose is to show how a visual language can communicate different relationships explicitly.

A robust editor should validate these relationships continuously, ideally providing useful explanations when a connection is invalid.

#### 8.3 Treat types as a visual design problem

Types can be represented using labels, port shapes, colors, annotations, or contextual information.

A useful type system can prevent many mistakes, but visual type indicators must be consistent and accessible. Color alone is insufficient; the type should also be communicated through text, symbols, or other cues.

A language designer must decide whether to use:

- Static typing.
- Dynamic typing.
- Type inference.
- Generic or polymorphic operations.
- Implicit conversions.
- Domain-specific types such as vectors, textures, signals, or physical units.

Domain-specific types can be particularly powerful. For instance, an editor for engineering calculations could distinguish a temperature from a distance rather than treating both as undifferentiated numbers.

#### 8.4 Make abstraction a first-class feature

Large visual programs need mechanisms to manage complexity.

Useful features include:

- Functions and reusable subgraphs.
- Modules and namespaces.
- Parameters and generic components.
- Local variables and controlled state.
- Interfaces between components.
- Documentation and contracts.
- Testing at component boundaries.

Without these features, users tend to duplicate large graphs or create monolithic visual programs. The resulting complexity can outweigh the benefits of the visual representation.

#### 8.5 Separate program structure from its layout

This is a particularly promising design direction.

Imagine that a program has a stable underlying graph of nodes, connections, types, and identifiers. The editor can display that program as a compact graph, a hierarchical outline, a table, or a textual representation.

The key is that changing the presentation should not unintentionally change the program's meaning.

Such separation can improve:

- Automatic layout.
- Multiple views of the same program.
- Version control.
- Collaboration.
- Search and navigation.
- Automated refactoring.
- Accessibility.

It also creates a more precise foundation for translating between visual and textual programming.

### 9. A reference architecture for a modern VPL

The following is a proposed architecture for research and design, rather than a description of any one product.

#### 1. Visual editor

Nodes, blocks, connections, layout, selection, interaction

#### 2. Structured program representation

Stable IDs, typed nodes, graph edges, scopes, metadata

#### 3. Language analysis

Grammar validation, type checking, name resolution, diagnostics

#### 4. Execution or compilation

Interpreter, compiler, scheduler, runtime, or code generator

#### 5. Runtime and development feedback

Execution traces, values, errors, profiling, tests, live updates

Each layer has distinct responsibilities.

The editor manages interaction and presentation. It should not be the sole authority on the program's semantics.

The structured representation stores the actual program. A typed graph is one possibility, but hierarchical syntax trees or hybrid representations may be more suitable for other language designs.

Language analysis determines whether the program is valid and provides actionable diagnostics.

Execution or compilation translates the representation into behavior, using an interpreter, a compiler, or an execution engine.

Feedback mechanisms expose the program's behavior and performance to the user.

A persistent structured representation also makes it easier to support multiple editors, text-based editing, external tools, and AI-assisted transformations.

#### Should a VPL generate textual code?

Not necessarily. There are at least three viable strategies.

| Strategy              | How it works                                                                                 | Main trade-off                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Direct interpretation | The runtime executes the visual program's internal representation.                           | Straightforward semantic control, but runtime overhead may matter.                                 |
| Compilation           | The program is translated into machine code, bytecode, or another executable representation. | Enables optimization, but requires a reliable compiler and diagnostics mapping.                    |
| Code generation       | The program generates source code in another language.                                       | Improves interoperability, but the target language may not preserve all source-language semantics. |

A hybrid system can support several of these approaches.

For example, a VPL might interpret graphs during interactive development, compile them for deployment, and generate textual source for interoperability. The important requirement is that the language's meaning remains consistent across execution modes.

### 10. Can visual programming be general-purpose?

The Wikipedia article names PWCT and Envision as research efforts aimed at general-purpose visual programming. This is a particularly important direction because many established VPLs excel within a domain but are less convenient for arbitrary software development.

The difficulty is not simply adding more nodes.

A general-purpose language must support the full range of abstractions needed for large software systems: functions, data structures, modules, libraries, error handling, concurrency, testing, version control, deployment, and maintenance.

It must also compete with textual languages on the speed of editing, the cost of expressing complex logic, and the quality of existing development tools.

#### The scalability problem

Visual programs consume two-dimensional space. Textual programs also have navigation problems, but they can be compact, searched efficiently, edited with keyboard-oriented workflows, and compared using line-based tools.

Large visual graphs can suffer from:

- Excessive scrolling and zooming.
- Long-distance connections.
- Dense crossings between edges.
- Repetitive structures that are cumbersome to construct.
- Poorly localized changes.
- Difficult diffs and merges.

These problems are not inevitable, but solving them requires language and editor design, not just a better layout algorithm.

Research into general-purpose visual programming has emphasized the need for efficiency comparable to textual development environments. Envision, for example, explicitly pursued general-purpose software development and efficient visual representations.&#x20;

Programming Methodology Group

#### A plausible alternative: visual-first, not visual-only

A modern general-purpose VPL need not insist that every expression be represented as a node.

It could use a combination of:

- Graphs for dependencies and high-level architecture.
- Textual expressions for dense mathematical or symbolic operations.
- Structured forms for configuration.
- Tables for data-oriented definitions.
- State diagrams for reactive behavior.
- Generated or embedded textual code for specialized tasks.

The goal would be to select the best representation for each part of a program while preserving a coherent language and development environment.

This leads to a broader research question:

Is a universal visual notation desirable, or should general-purpose programming use a shared computational model with multiple interchangeable representations?

The second approach may offer a more practical way to combine visual programming's strengths with the efficiency of text.

### 11. Visual programming and AI-assisted development

AI introduces a new dimension to visual programming research.

An AI system may generate a graph, explain a program, diagnose a failed connection, suggest a refactoring, or translate between a visual language and text. However, a graph is more than an image: it has node identities, typed edges, scopes, execution rules, and structural constraints.

A system that produces a visually plausible graph may still generate an invalid or semantically incorrect program.

A 2026 survey of research on large language models and visual programming identified a mismatch between graph-structured programs and the linearized representations commonly used by AI systems. It also highlighted limited standardization in evaluation.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.sciencedirect.com\&sz=32)

ScienceDirect

#### Promising research directions

Structure-aware program generation

Generate nodes, edges, types, and scopes as explicit structured data instead of relying exclusively on screenshots or flattened graph descriptions.

Constraint-guided repair

Use compiler errors, type constraints, and execution traces to repair invalid or incorrect programs while preserving valid existing structure.

Bidirectional visual-textual development

Let users move between a graph and source code while preserving program meaning and identifying constructs that cannot be represented identically in both views.

Explainable debugging

Use runtime observations to explain why a node executed, why a value changed, or why a particular output was produced.

A particularly interesting possibility is to treat the language's formal representation as the shared interface between the human, the editor, the compiler, and the AI assistant.

That would allow the AI to reason over the actual program structure rather than inferring everything from how it happens to be drawn.

### 12. How should VPLs be evaluated scientifically?

This is where a research project can move beyond subjective comparisons such as “blocks feel easier” or “graphs are more intuitive.”

A useful evaluation should measure several independent properties.

| Dimension               | Possible measures                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------- |
| Learnability            | Time to complete introductory tasks; retention after a delay                          |
| Construction efficiency | Time, number of interactions, number of corrections                                   |
| Expressiveness          | Range and complexity of programs that can be represented naturally                    |
| Comprehension           | Accuracy and speed when explaining an existing program                                |
| Debuggability           | Time to locate a fault and correctness of the repair                                  |
| Maintainability         | Cost of extending, refactoring, and understanding larger projects                     |
| Scalability             | Performance and usability as graph size and complexity increase                       |
| Reliability             | Frequency of runtime failures and incorrect outputs                                   |
| Accessibility           | Success with keyboard navigation, assistive technologies, and varied visual abilities |
| Interoperability        | Fidelity of imports, exports, translations, and version-control operations            |

These measures should not be collapsed into a single “ease of use” score. A language might be excellent for novice construction but poor for refactoring, or highly expressive but difficult to learn.

#### A possible comparative study

Suppose you wanted to compare three representations of the same computational model:

- A textual language.
- A block-based language.
- A node-graph language.

You could give participants equivalent programming tasks, control for prior experience, and measure both initial performance and later maintenance.

Tasks might include:

1. Implementing a simple algorithm.
2. Adding a new feature to an existing program.
3. Finding a logic error.
4. Understanding an unfamiliar program.
5. Refactoring repeated logic into a reusable component.

The experiment should distinguish interface familiarity from the effect of the representation itself. It should also report participant backgrounds, task complexity, and uncertainty in the results.

This is especially important because visual-programming research has historically contained gaps in rigorous empirical evaluation. The systematic review of end-user visual programming approaches and earlier reviews of visual programming effectiveness both provide useful starting points for understanding these methodological challenges.&#x20;

### 15. A proposed research agenda

If I were turning this expanded overview into a sustained research project, I would organize it around six questions.

1. Representation and cognition: Under what conditions do graphs, blocks, diagrams, and text improve program comprehension? How do experience, task complexity, and familiarity change the results?
2. Expressiveness and scalability: Which language features become awkward in visual form, and which benefit from spatial representation? Can hierarchical and hybrid views overcome these limits?
3. Semantics and correctness: How can a VPL precisely define types, execution order, concurrency, side effects, and error behavior? Which constraints can the editor enforce?
4. Interoperability: How can visual and textual representations coexist without losing semantics, producing unmanageable diffs, or tying programs to one editor?
5. Empirical evaluation: Which measurements and experimental designs best distinguish learnability, construction speed, comprehension, debugging, and long-term maintenance?
6. AI-assisted programming: How can AI manipulate structured visual programs reliably, explain changes, preserve constraints, and validate its results?

These questions connect the article's diverse examples into a more coherent research program. They also help identify the difference between improving an editor, inventing a visual notation, and designing a genuinely new programming language.

### Conclusion

The most important takeaway is that visual programming is not one paradigm. It is a family of languages and environments that use graphical representations to express computation, with different computational models, audiences, and design goals.

The most successful visual approaches tend to exploit a natural correspondence between the representation and the problem being solved. Blocks can make introductory control structures approachable; node graphs can expose data dependencies; state diagrams can clarify reactive behavior; and engineering diagrams can correspond closely to physical systems.

The major unresolved challenge is scaling visual programming from accessible, domain-specific construction to maintainable, expressive, interoperable software development. That challenge involves semantics, abstraction, tooling, empirical evaluation, and human-computer interaction—not just the appearance of the editor.

A strong research perspective therefore asks three questions of every VPL:

1. What computations can it express, and what are their precise semantics?
2. What does its visual representation make easier or harder for people to construct, understand, debug, and maintain?
3. What evidence demonstrates that it succeeds for its intended users and tasks?

Those questions provide a more durable foundation for studying visual programming than any list of products alone.
